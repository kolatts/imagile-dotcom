An agent finishes a task and tells you what it did. One sentence, confident, agreeable. It sounds like a report.

It isn't. It's a claim, generated by the same process that did the work, checked against nothing. The only account of what actually happened is the diff — the exact lines that changed between two points in your history. Nobody wrote it. A program that has no opinion about whether you're pleased produced it.

That distinction is the whole discipline. Everything else in this post is just what falls out of taking it seriously.

## Forty Files, Ninety Seconds, One Sentence

Turn an agent loose on a real task and it will touch far more of your codebase than a human would in the same stretch of time. Forty files changed, ninety seconds elapsed, and then a summary: "Rewrote the export button, everything green."

That sentence is doing a lot of compression. It's also the only thing standing between you and thirty-eight files you haven't looked at. The gap between "the agent said it worked" and "you know it worked" is exactly the size of the diff you didn't read.

This is why the habit has to be mechanical, not situational: commit before you turn an agent loose, and commit again after you've checked its work. Every run then sits bracketed between two snapshots you personally trust. That costs about four seconds, twice. Compare that to the cost of finding out three weeks later that the "unrelated tidy-up" in file six broke something nobody was watching.

The failure mode is never too many commits. It's one enormous commit holding eleven agent edits, three of which were wrong, now welded to the eight that were right, with no way to pull them apart.

## Read It Before You Trust It

The review loop is short and it doesn't change: the agent finishes, you run `git status` to see what's different, you run `git diff` to see exactly what changed, you decide, and you commit — or you put it back. Then the next run starts from a point you actually verified, not one you were told about.

That last step is the one people skip, because the summary already told them what they'd find. That's the whole problem with the summary. It's written to be agreeable. It was written by the thing you're trying to check.

## The Commit Message Is a Briefing, Not a Caption

A commit with no useful message is a photograph with no caption — the snapshot records *what changed*, the message is the only place *why* can live. Write it for the stranger who'll read it later, who is you, tired, in three weeks.

The stranger is also, increasingly, not a person. An agent reads your commit log before it touches a project it doesn't know — that log is its briefing for the work ahead. A history of `fix`, `fix2`, and `ok now` briefs it exactly that well, which is to say not at all. A message that states what changed and why hands the next session a starting point instead of a guessing game.

## The One Thing Git Can't Give Back

There's a second decision hiding inside "choose what goes into the commit," and it's the only one in this whole discipline that can't be undone: what must never enter the history at all.

Anything holding a secret — a password, an API key, an access token — usually means a file called `.env`. Declare what's off-limits once, in a `.gitignore` at the project root, before the first commit. Not after. The order matters more than the content, because of what happens if you get it backwards.

If a secret was ever committed, deleting the file does not remove it from history. Every past state in git is still reachable, including the one where the key sat in plain text — that's the same property that makes the whole system useful, pointed the wrong way. Deleting the file just writes a new snapshot without the secret and leaves the old one, one step back, fully intact.

So the fix for a leaked key isn't deleting the file. It's rotating the secret. And an agent reads your whole working directory, so a credentials file sitting in the workspace is in its field of view whether you meant it to be or not — it will happily quote the thing back at you in a summary. Ignoring the file keeps it out of history. Keeping credentials outside the project directory entirely keeps them out of the conversation.

## This Is the Judgment We Train, Not the Commands

None of this is a git tutorial. `git status` and `git diff` are two commands anyone can learn in an afternoon. Knowing to run them, every time, before you trust a summary you didn't write — that's judgment, and it doesn't show up in the man page.

That's the gap our developer training at Imagile is built to close. Tool literacy is cheap now; the models will teach you the flags. What's scarce is the discipline to treat an agent's account of its own work as a claim requiring evidence, on every single run, especially the ones that feel routine. The diff was always the evidence. Agents just made it possible to go a lot longer without reading one.
