An agent stops working the moment the result looks finished. Not when it's correct — when it looks done.

If nothing else is checking, that's the only signal it has. Every mistake it made along the way just sits there, waiting for you to be the one who notices.

## You Didn't Apply for This Job

Here's the sentence the rest of this depends on: you are the verification loop, by default, whether you signed up for it or not.

A good plan doesn't get you out of it. A focused agent doesn't get you out of it. A well-briefed subagent doesn't get you out of it. The only thing that does is a check the agent can run itself and read the answer to, without asking you first.

A check just means something that says pass or fail. A test suite. A build that either finishes or doesn't. A screenshot compared against what the page is supposed to look like. Nothing fancy — the whole point is that it works without a person in the room.

## Four Things You Can Hand the Agent

**Tell it what "done" means.** Say up front, in plain language, what the finished result has to actually do. Then the agent checks the real result against that statement instead of you taking its word for it. You stop having to guess afterward whether "looks done" and "is actually done" were ever the same thing.

**Give it the old tests to run.** Hand over the existing regression suite with instructions to run all of it after a change, not just the part it touched. You stop having to click through the rest of the app by hand to confirm nothing old broke.

**Give it eyes on the screen.** A browser it can open and click around in — through MCP, the standard way a harness reaches tools outside itself — so it sees the actual page the way a person would, instead of just reading its own code back to itself. You stop being the first set of eyes on whether the change actually works, or just reads like it should.

**Have it review its own diff first.** Before a human review starts, have the agent read back over its own changes the way a reviewer would: the leftover debug code, the wrong file touched, the approach that quietly drifted from what was asked. Tell it to flag only what's actually broken — asked to review, it will always find something. You stop being the first reviewer catching the obvious stuff, and start reviewing something that already survived one pass.

## One of These Actually Removes the Work

The other three catch mistakes sooner. The second one removes a whole category of work permanently.

End-to-end tests, run locally in the same place the work already happens, don't just catch bugs earlier — they take manual QA off that path entirely, now rather than later. Write the suite once and nobody clicks through those flows by hand again. That's the difference between a faster check and no check required.

## Verification Isn't the Last Step

It's easy to picture verification as the finish line — the thing that happens after the real work, before you move on. It's actually where the next round starts. Whatever the check turns up is the input to what the agent does next, which makes checking and planning the same motion, not two separate ones.

Two quieter payoffs are worth naming. A check catches a wrong turn while it's still one wrong turn, so the agent fixes it on the spot instead of building three more things on top of a mistake — cheaper than the archaeology later, and it keeps shipped work from regressing. And the time comes back to you: while the agent runs its tests and clicks through its own screens, you're not standing behind it watching. The checking and the deciding-what's-next happen at the same time, on different desks.

Spell-check didn't replace writers. It replaced *asking* whether anyone proofread — nobody circulates a memo wondering if the typos got caught, because the machine underlines them as they happen. Giving an agent its own checks is the same move for finished work. It doesn't make you obsolete. It makes "did anyone verify this?" an obsolete question, one check at a time.

## Evidence, Not Assertions

"I verified this works correctly" is not a check. It's a sentence.

Test output. A command and what it returned. A screenshot of the actual flow. That's evidence. An agent telling you it verified something is an assertion wearing evidence's coat, and the two are easy to confuse right up until the moment they diverge.

If nothing else checks the work, "looks done" is all an agent has to go on — which makes you the verification loop, by default, until you build something that takes the job instead. None of the four things above replace you looking at the result. They raise the floor on what arrives at your desk before you do.
